# AnyAlgebra v0.0 specification

Status: Proposed implementation contract  
Roadmap label: `v0.0`  
Semantic-version target: `0.0.0`  
Last updated: 2026-07-22

## 1. Purpose

Version 0.0 is the smallest trustworthy substrate on which later mathematical
families and research projects can be built. It must represent structures the
package has never heard of, including many-sorted relational structures and
partial operations. It must also support the finite multilinear algebras needed
to reproduce the sound foundational behavior of `AlgMul` without copying its
global-state or metaprogramming design.

Version 0.0 is a foundation release, not a claim that AnyAlgebra already
implements Lie theory, Clifford algebras, division-algebra linear groups, E8, or
any research result. No portfolio project is declared complete by this release.

## 3. Required user outcomes

A v0.0 user can:

1. define exact scalar domains and explicit coercions;
2. define sorts, finite carriers, bases, free modules, and sparse elements;
3. declare arbitrary operation and relation signatures;
4. construct total or partial operations without defining a Python subclass;
5. distinguish mathematical undefinedness, unsupported capability, bounded
   indeterminacy, and computational failure;
6. evaluate fully parenthesized terms without silently imposing associativity;
7. construct a finite multilinear algebra from tables, callables, or structure
   constants;
8. convert among symbolic, coordinate, table, structure-constant, and operator
   presentations through explicit, auditable conversion maps;
9. recover structure constants from exact operators when closure and uniqueness
   are proved, and receive witnesses when they are not;
10. state laws, validate them exactly on bounded finite domains or on a basis
    when a theorem justifies the reduction, and receive counterexamples;
11. compute elementary invariants such as commutators, associators, nuclei,
    center, ideals, and derivations for bounded exact fixtures;
12. serialize semantic objects safely and replay a calculation from a receipt;
13. locate every audited `AlgMul` capability owned by v0.0 in a parity manifest
    with a typed replacement, corrected replacement, deferred status, or defect
    disposition.

## 4. In scope

### 4.1 Exact domains and coercions

- canonical integer and rational domains, `ZZ` and `QQ`;
- exact domain elements with canonical normalization;
- explicit injective coercions and an immutable coercion graph;
- automatic coercion only when the lossless path is unique;
- parent-aware equality and hashing as specified by ADR-0002.

Floating-point, interval, symbolic, algebraic-number, finite-field, and modular
domains may exist as experiments, but are not public v0.0 commitments.

### 4.2 Neutral mathematical core

- named sorts and finite carriers;
- bases, finite free modules, coordinate vectors, and sparse elements;
- operation symbols of arbitrary finite arity and relation symbols;
- signatures, terms, variables, equations, laws, and law sets;
- total and partial table-backed or callable operations;
- relations, reduction systems, and finite deductive systems;
- a general `Structure` root that is not restricted to magmas or algebras;
- finite multilinear structures as one specialization of that root.

### 4.3 Presentations and maps

- symbolic, coordinate, table, structure-constant, and matrix/operator
  presentations;
- explicit conversions registered in an immutable conversion graph;
- exact round trips, basis changes, span decomposition, and closure checks;
- linear, multilinear, and structure-preserving maps;
- no implicit reinterpretation based only on Python container shape.

### 4.4 Evaluation and validation

- parenthesized term evaluation;
- explicit evaluation outcomes;
- bounded exhaustive validation over declared finite carriers;
- basis-reduced validation only when the law's multilinearity and hypotheses are
  recorded;
- counterexample and smallest-witness reporting;
- elementary nonassociative analysis for finite exact algebras.

### 4.5 Evidence and persistence

- immutable convention manifests, source anchors, calculation contracts, result
  receipts, and artifact hashes;
- tagged, schema-versioned JSON for all stable public data models;
- canonical serialization suitable for hashing;
- replay checks that reject changed inputs, versions, conventions, or backends;
- first-class negative and inconclusive results.

### 4.6 Legacy ownership

Version 0.0 owns the audited `AlgMul` partitions for:

- algebra/basis registration and multiplication-table lookup;
- symbolic-list-coordinate conversion;
- tensor, matrix, and matrix-over-tensor lifting mechanisms;
- structure-constant recovery and span decomposition;
- runtime-generated elementary property families that map to v0.0 laws and
  analyses;
- generic element construction over finite bases.

Specialized Clifford, spinor, Lie, Jordan, exceptional, and group experiments
are audited now but normally deferred to their owning releases. A capability is
not silently dropped merely because its replacement is deferred.

## 5. Explicit non-goals

Version 0.0 does not promise:

- specialized public constructors for `R`, `C`, `H`, `O`, their split forms,
  Clifford algebras, Lie algebras, Jordan algebras, or exceptional groups;
- universal definitions of `GL(n,A)`, `SL(n,A)`, `SO(n,A)`, or `SU(n,A)`;
  those remain mandatory later program requirements;
- polynomial Gröbner bases, Knuth-Bendix completion, category-theory machinery,
  root and weight systems, invariant discovery, manifolds, fields, variational
  calculus, or Schouten integration;
- performance superiority over Mathematica, SageMath, GAP, or specialized
  numeric libraries;
- automatic proof of a manuscript claim;
- treating legacy output as a correctness oracle;
- executing arbitrary code during deserialization;
- choosing a mathematical convention implicitly.

## 6. Public object boundary

The normative public names are listed in [api-v0.0.md](../api/api-v0.0.md).
Everything else is private unless promoted by a later accepted specification.
Public objects follow these rules:

- parents and semantic values are immutable;
- all elements know their parent;
- equality never performs a lossy or ambiguous coercion;
- operations return explicit outcomes where partiality or bounded computation
  is possible;
- backend-specific objects do not leak through the neutral API;
- every serialized object carries a schema type and version;
- every scientific calculation can emit a receipt.

## 7. Dependency policy

The reference kernel uses the Python standard library plus the smallest pinned
set of dependencies justified by tests. Optional adapters are isolated behind
capability interfaces. NumPy, SymPy, SciPy, SageMath, GAP, Mathematica,
Schouten-kit, and proof assistants must not become required merely to import the
neutral core.

The exact reference backend is normative for semantics. Optimized backends may
accelerate operations only after differential tests demonstrate agreement on
their declared capability domains.

## 8. Required examples

The release must ship executable examples for:

1. a user-defined three-element partial magma with an undefined product;
2. a finite deductive system with modus ponens as a relation/rule fixture;
3. an arbitrary two-sorted structure containing a relation and a ternary
   operation;
4. a rational algebra created from structure constants;
5. exact symbolic-coordinate-table round trips;
6. operator closure and structure-constant recovery, including a nonclosure
   witness;
7. quaternion and octonion fixture tables loaded through generic APIs, not
   specialized classes;
8. an associativity failure with an explicit octonion counterexample;
9. a generated `AlgMul` property-family entry mapped to one typed law factory;
10. receipt creation, serialization, reload, and replay verification.

These examples prove infrastructure behavior only. Their familiar names do not
promote specialized algebra-family APIs into v0.0.

## 9. Acceptance gates

Version 0.0 is acceptable only when all of the following hold:

- every public API ID in the v0.0 process scope has documentation and tests;
- all in-scope actions link to a feature, story, and observable test;
- every ADR is accepted or the release is explicitly blocked on it;
- all exact finite fixtures within declared bounds are exhaustively checked;
- every partiality branch is tested and serializes distinctly;
- conversion round trips and failure witnesses pass for at least two unrelated
  associative and two unrelated nonassociative fixtures;
- the exact backend passes all normative tests;
- at least one optional backend, if present, passes differential tests or is
  clearly labeled experimental and excluded from the public release;
- unsafe or unknown serialized type tags are rejected;
- a clean environment can install, run examples, run tests, and rebuild docs;
- the `AlgMul` source hash, kernel version, load status, generated-symbol audit,
  registry snapshot, and disposition coverage are recorded;
- no v0.0-owned legacy entry remains unclassified;
- known legacy defects have regression tests that require the corrected result,
  not bug-for-bug reproduction;
- no research project or scientific claim is marked verified merely because
  this foundation release passes.

## 10. Exhaustive testing boundary

“Exhaustive” means all cases in the declared finite parameter grid, not all
mathematics. Each exhaustive test records its domains, carrier sizes, term depth,
coefficient bounds, and convention manifest. Random or sampled checks are useful
additional evidence but cannot replace a declared exhaustive gate.

The minimum finite grid includes:

- all binary products for every shipped finite table fixture;
- all triples for associativity/alternativity fixtures whose basis-reduction
  theorem applies, otherwise all elements in the declared finite coefficient
  box;
- all defined and undefined entries in partial-operation fixtures;
- all conversion paths in the shipped conversion graphs;
- all registered coercion-path ambiguity cases;
- all serialization tags and schema-rejection branches;
- every v0.0-owned `AlgMul` parity partition and runtime symbol family.

## 11. Release artifacts

- installable Python package and locked development environment;
- API reference and executable examples;
- machine-readable project-process registries;
- accepted ADRs and convention manifests;
- test report with exhaustive bounds and backend matrix;
- `AlgMul` static/evaluated surface manifest and parity disposition table;
- JSON Schemas or equivalent validators for stable serialized records;
- release notes, known risks, and carryover record.

## 12. Change control

Adding a convenient class is not sufficient reason to expand v0.0. A proposed
addition must identify a v0.0 user outcome, API ID, story, test, serialization
impact, and architecture consequence. Otherwise it belongs in a later version.
Semantic changes to parenthood, equality, coercion, partiality, evidence, or
serialization require a superseding ADR.
